# /cc:4아키텍처리뷰 — 아키텍처 리뷰어

> 프로젝트 전체 설계, 성능, 확장성, 운영 안정성을 시니어 아키텍트 관점에서 리뷰한다.
> 월 1회 또는 큰 기능 변경 후 실행한다.

## 입력
$ARGUMENTS

---

## Phase 1: 리뷰 범위 결정

### 인자가 있는 경우
- `$ARGUMENTS`에 특정 영역이 있으면 해당 영역만 심층 리뷰
- 예: `/cc:4아키텍처리뷰 성능` → 성능 영역만 집중 리뷰
- 예: `/cc:4아키텍처리뷰 src/api/payments` → 결제 도메인 아키텍처만

### 인자가 없는 경우 (전체 리뷰)
아래 6개 영역을 모두 리뷰한다.

## Phase 2: 리뷰 영역

### 2-1. API 설계 (Design)

- [ ] **중복 로직**: 여러 API에 동일한 비즈니스 로직이 복사-붙여넣기 되어 있지 않은가?
  - 해결: 공통 미들웨어/유틸 함수로 추출
- [ ] **관심사 분리**: 하나의 API가 너무 많은 일을 하고 있지 않은가? (200줄 이상 주의)
- [ ] **URL 설계**: RESTful 원칙을 따르는가? (동사 대신 명사, 중첩 리소스)
- [ ] **API 간 의존**: API A가 내부에서 API B를 호출하는 패턴이 있는가? (직접 함수 호출 권장)
- [ ] **파일 구조**: 도메인별로 잘 분리되어 있는가?

### 2-2. DB 성능 (Performance)

- [ ] **인덱스 활용**: WHERE 절에 자주 사용되는 컬럼에 인덱스가 있는가?
- [ ] **풀 테이블 스캔**: 큰 테이블에서 인덱스 없이 조회하는 쿼리
- [ ] **SELECT 최적화**: 필요한 필드만 가져오는가? (전체 컬럼 조회 지양)
- [ ] **카운트 쿼리**: `count()`가 비효율적으로 사용되는 곳
- [ ] **커넥션 풀**: DB 클라이언트가 싱글턴으로 관리되는가?
- [ ] **느린 쿼리 후보**: JOIN이 3개 이상이거나 서브쿼리가 중첩된 쿼리

### 2-3. 확장성 (Scalability)

> "사용자가 현재의 10배가 되면 어디가 터지는가?"

- [ ] **동시 접속**: 세션 관리 방식이 서버 수평 확장에 대응하는가?
- [ ] **파일 업로드**: 로컬 파일 시스템에 저장하는가? (S3/CDN 권장)
- [ ] **캐싱 전략**: 자주 조회되지만 변경이 적은 데이터에 캐시가 있는가?
- [ ] **백그라운드 작업**: 무거운 작업이 API 요청 안에서 동기로 실행되는가?
- [ ] **DB 커넥션**: 동시 요청이 많을 때 커넥션 풀이 충분한가?
- [ ] **메모리 사용**: 대량 데이터를 메모리에 한 번에 올리는 곳이 있는가?

### 2-4. 의존성 건강도 (Dependencies)

- [ ] **deprecated 패키지**: 더 이상 유지보수되지 않는 패키지
- [ ] **보안 취약점**: `npm audit` / `pip audit` 등 결과에 high/critical
- [ ] **버전 고정**: 주요 패키지 버전이 느슨해서 예기치 않은 업데이트 가능성
- [ ] **중복 기능**: 같은 역할의 패키지가 2개 이상
- [ ] **번들 크기**: 불필요하게 큰 패키지가 클라이언트에 포함되는가?

### 2-5. 에러 복구 & 장애 대응 (Resilience)

- [ ] **DB 연결 끊김**: 자동 재연결되는가?
- [ ] **외부 API 타임아웃**: 타임아웃 설정이 있는가?
- [ ] **재시도 전략**: 일시적 실패에 대해 재시도 로직이 있는가?
- [ ] **서킷 브레이커**: 외부 서비스 장애 시 연쇄 실패 방지 메커니즘
- [ ] **Graceful Shutdown**: 배포 시 진행 중인 요청이 완료될 때까지 대기하는가?
- [ ] **헬스체크**: 앱 상태를 확인하는 엔드포인트가 있는가?

### 2-6. 모니터링 & 로깅 (Observability)

- [ ] **에러 추적**: 에러 발생 시 어디서 터졌는지 빠르게 찾을 수 있는가?
- [ ] **성능 모니터링**: 느린 API 응답을 감지할 수 있는가?
- [ ] **로그 수준**: 로그가 너무 많지도, 적지도 않은가? (민감 정보 로깅 금지)
- [ ] **알림**: 심각한 에러 발생 시 개발팀에 알림이 오는가?
- [ ] **대시보드**: 시스템 상태를 한눈에 볼 수 있는 모니터링이 있는가?

## 실행 규칙

1. **전체를 본다** — 파일 단위가 아니라 시스템 전체의 흐름과 구조를 본다
2. **숫자로 말한다** — "느릴 수 있다"가 아니라 "N건 테이블에 인덱스 없이 풀스캔" 등 구체적으로
3. **현실적 제안** — MVP 속도가 중요한 팀에 맞는 수준의 제안 (과도한 엔터프라이즈 패턴 지양)
4. **난이도를 표시한다** — 각 제안에 구현 난이도 (쉬움/보통/어려움) 포함
5. **코드를 직접 수정하지 않는다** — 리포트만 출력, 수정은 사용자 승인 후
6. **이전 리포트와 비교** — 이전 리뷰 결과가 있으면 개선/악화 추이를 표시
